# gitless-sync — PRD (v0.2.1)

## 한 줄 요약

git이 없는 로컬 디렉토리를 GitHub repo와 단방향으로 비교해, 드리프트를 정량적으로 보고하는 read-only AI 친화 CLI.

## 배경 / 문제

- 일부 환경(예: iCloud 동기화 디렉토리)에서는 `git init` 자체가 불가능하다. iCloud의 파일 시스템 간섭이 git 메타데이터를 깨뜨리는 사례가 있어, 같은 디렉토리를 다른 환경에서 git으로 관리하더라도 이 환경에서는 git을 쓸 수 없다.
- 이 환경에서 GitHub repo에 변경을 반영하려면 수동 push에 의존해야 하고, 누락된 push가 다른 환경의 작업과 시간차로 어긋나면 "평행우주 드리프트"가 발생한다.
- 매번 LLM에 "이 디렉토리와 GitHub repo의 차이를 알려줘" 같은 부탁을 반복하는 건 비결정적이고 비효율적이다. 정량적·재현 가능한 도구가 필요하다.

## 목표 (Goals)

- 로컬 디렉토리와 GitHub repo의 모든 파일을 **전수 비교**해 4분류 결과를 JSON으로 출력한다.
- AI(또는 사람)가 결과를 받아 다음 행동을 결정할 수 있도록, 도구는 **사실만 제공**하고 결정은 하지 않는다.
- 도구는 vault·노트 같은 특정 도메인에 종속되지 않는다. 임의 로컬 디렉토리와 임의 GitHub repo 간 비교가 가능해야 한다.
- Windows를 1차 타겟 환경으로 안정 동작.
- read-only 보장. 파일 쓰기·원격 변경은 비목표(별도 도구로 분리).

## 비목표 (Non-Goals, v0.1)

- 3-way merge / 자동 충돌 해결.
- 양방향 동기화. 단방향 비교만 제공.
- 파일 실제 쓰기·삭제 (read-only 도구).
- GitHub 외 다른 호스팅(GitLab, Bitbucket 등) 지원.
- LFS 추적 파일.
- 인터랙티브 UI.
- (Phase 5에서 다룰 도메인 함정 — 비목표가 아니라 *후속 단계*: 아래 Phase 로드맵 참조)

## 핵심 사용 사례

- "지금 내 로컬 디렉토리와 GitHub main 브랜치의 차이를 한 번에 보여줘."
- AI 어시스턴트가 도구 호출 → JSON 결과를 파싱 → 사용자에게 정리된 변경 목록 보고 → 사용자 승인 후 별도 도구(`gitless-push`, Phase 3)로 push.

## 아키텍처

**Vertical slice — 명령어 단위.**

```
src/
├── main.rs              # CLI 인자 파싱, 명령어 디스패치
├── commands/
│   ├── scan/            # scan 명령어 자체 모듈
│   │   ├── mod.rs       # 명령어 entry point
│   │   ├── github.rs    # Trees API 호출 (ureq, blocking)
│   │   ├── walker.rs    # 로컬 디렉토리 walk
│   │   ├── compare.rs   # 4분류 판정
│   │   └── output.rs    # JSON 직렬화
│   └── diff/            # diff 명령어 자체 모듈
│       ├── mod.rs
│       └── ...
└── shared/              # 공통 컴포넌트
    ├── hash.rs          # LF-normalized blob hash 계산
    ├── normalize.rs     # LF normalize, BOM 처리
    ├── ignore.rs        # .gitignore + --ignore 통합
    ├── error.rs         # custom error types (thiserror)
    └── config.rs        # 설정 파일 / env 로드
```

원칙:
- 명령어는 자체 모듈에서 완결. 명령어 추가 시 다른 명령어 코드를 건드리지 않음.
- `shared/`는 진짜 공통(여러 명령어가 동일 로직 사용)만 들어감.
- HTTP 클라이언트는 **blocking (`ureq`)**. async 도입은 명시적 요구가 발생할 때까지 보류.
- 모듈 가시성은 `pub(crate)`로 슬라이스 경계 강제.

## CLI 인터페이스 (v0.1)

- `gitless-sync scan` — 비교 실행, 4분류 결과를 stdout JSON으로 출력
- `gitless-sync diff <path>` — 특정 파일의 raw text diff 출력

공통 플래그:

- `--repo <owner/name>`
- `--branch <name>` (기본 `main`)
- `--local <path>` (기본 cwd)
- `--ignore <pattern>` (반복 가능, gitignore 문법)
- `--token <env|literal>` (기본 `$GITHUB_TOKEN`. 형식: `env:<name>` 또는 `literal:<value>`)
- `--keep-bom` (기본 false; UTF-8 BOM 보존 모드)
- `--json` (기본) / `--pretty`

`scan` 전용 플래그 (컨텍스트 폭발 방어):

- `--summary-only` — `files[]` 배열 빼고 `summary` 객체만 출력. 큰 vault에서 LLM 컨텍스트 절약.
- `--status <list>` — 콤마 구분 enum 필터. 예: `--status drift,local_only_changed`. 지정한 status 파일만 `files[]`에 포함.

## 핵심 알고리즘

1. GitHub Trees API(`GET /repos/{owner}/{repo}/git/trees/{branch}?recursive=1`)로 원격 전체 파일 목록 + blob SHA 수집. 1회 호출. `truncated: true` 응답 시 v0.1은 빠른 실패 (exit code 5).
2. 로컬 디렉토리 walk → 각 파일에 **LF-normalized blob hash** 계산.
3. 텍스트 파일은 비교 전 LF normalize, UTF-8 BOM 제거(`--keep-bom`이 아닐 때). 바이너리는 NUL 바이트 휴리스틱으로 판별, normalize 건너뜀.
4. 경로 기준 union으로 양쪽 SHA 비교 → 4분류.
5. 차이가 있는 파일에 한해, 추가 메타(`local_mtime`, `remote_last_commit_at` via Commits API) 채움.

### 해시 정의 (중요)

- 본 도구의 `local_sha`/`remote_sha`는 **git 표준 blob SHA가 아니다**.
- 정의: `SHA-1("blob <size>\0<LF-normalized content>")` (텍스트), `SHA-1("blob <size>\0<raw bytes>")` (바이너리).
- git의 표준 blob SHA는 working tree 바이트 그대로의 해시이며, `core.autocrlf` / `.gitattributes`의 영향을 받는다. 본 도구는 `.gitattributes`를 파싱하지 않으므로 git 표준 SHA를 정확히 재현할 수 없다.
- 결과적으로 GitHub UI나 `git hash-object`로 얻는 SHA와 본 도구의 SHA가 다를 수 있다. 본 도구의 SHA는 **"의미적 동일성"** (줄바꿈·BOM 차이는 동일로 간주) 비교를 위한 자체 정의 해시다.
- 원격 측 비교: GitHub Trees API가 반환하는 blob SHA는 실제 저장본의 SHA. 도구는 원격 blob을 다운로드 후 동일한 LF normalize 적용 → 자체 SHA 재계산해서 비교한다 (Trees API SHA는 무시).

## 4상태 분류

- `identical` — 양쪽 자체 SHA 동일.
- `local_only_changed` — 원격에 없거나 SHA 다른데 원격 last_commit ≤ 로컬 mtime. push 후보.
- `remote_only_changed` — 로컬에 없거나 SHA 다른데 로컬 mtime ≤ 원격 last_commit. pull 후보.
- `drift` — 양쪽 SHA 다르고 시간 비교로 한쪽 우위 판단 불가. 충돌 의심.

> 시간 비교 한계: 로컬 mtime은 touch·복사·iCloud 메타로 갱신되어 단조성이 없을 수 있다. `local_mtime == remote_last_commit_at` 동률은 `drift`로 격하한다. 최종 판단은 호출자(사람 또는 AI).

## Ignore 정책

- 로컬에 `.gitignore` 존재 시 자동 적용.
- `--ignore <pattern>` 인자(반복 가능) + 설정 파일 ignore 패턴은 `.gitignore`와 **합집합**으로 처리.
- 기본 ignore (도구 내장): `.git/`, `.DS_Store`, `Thumbs.db`, `desktop.ini`, `node_modules/`, `target/`. 이 목록은 `.gitignore`/사용자 인자와 합집합. 사용자가 명시적으로 끄려면 별도 미래 기능(현재 비목표).

## BOM 정책

- 기본: UTF-8 BOM 자동 제거 후 SHA 계산.
- `--keep-bom` 플래그: BOM 보존, byte-level 일치 요구.

## 운영 Contract (v0.1 필수)

read-only CLI라도 호출자(특히 AI)가 안정적으로 다룰 수 있도록 다음 6개 contract를 명시한다.

### Custom Error Types

`shared/error.rs`에 `thiserror` 기반 enum. 예시:

```rust
#[derive(thiserror::Error, Debug)]
pub enum GitlessError {
    #[error("Configuration error: {0}")]
    Config(String),
    #[error("Authentication failed")]
    AuthFailed,
    #[error("GitHub API rate limit exceeded (resets at {reset_at})")]
    RateLimitExceeded { reset_at: String },
    #[error("Tree response truncated; repo too large for v0.1")]
    TreesTruncated,
    #[error("I/O error: {0}")]
    Io(#[from] std::io::Error),
    #[error("Partial failure: {failed_count} files could not be hashed")]
    PartialFailure { failed_count: usize },
}
```

### Exit Code 매핑

- `0` — 정상 (drift 존재 여부와 무관)
- `1` — 사용자 입력 오류 (잘못된 인자, 파일 없음 등)
- `2` — 인증 실패 (`AuthFailed`)
- `3` — GitHub API 오류 (rate limit, 5xx 등)
- `4` — 부분 성공 (`PartialFailure` — 결과는 출력되지만 일부 파일 누락)
- `5` — Trees truncated (repo 너무 큼)

### stderr 출력 형식

stdout은 결과 JSON 전용. 모든 진행 로그·에러는 stderr.

stderr 에러는 구조화 JSON 한 줄:

```json
{"error_code": "AUTH_FAILED", "message": "GITHUB_TOKEN unauthorized", "context": {"status": 401}}
```

`error_code`는 `GitlessError` enum과 1:1 매핑. AI가 stderr 끝줄을 파싱해 처리 가능.

### stdout / stderr 분리 정책

- stdout: 결과 JSON만. 다른 출력 일체 금지.
- stderr: 진행 로그(verbose 레벨), 경고, 에러 JSON.
- verbose 플래그: `-v` (info), `-vv` (debug). 기본은 warning 이상만.

### Partial Failure 표현

일부 파일 해시 실패 시 전체 결과는 출력하되, `summary.failed_files` 카운트와 `files[].status: "failed"` (또는 별도 `failed[]` 배열) 표시. exit code 4.

### 인증 실패 / Rate Limit 초과 시 동작

- 인증 실패: 즉시 종료. exit code 2. 결과 JSON 출력 안 함.
- Rate limit 초과: 즉시 종료. exit code 3. stderr에 `reset_at` 시각 명시. 부분 결과 출력 안 함 (재시도하면 되므로).
- Trees API truncated: exit code 5. stderr에 안내. v0.1은 큰 repo 미지원.

## 출력 JSON 스키마 (v0.1)

```json
{
  "schema_version": "1.0",
  "scanned_at": "2026-04-27T10:30:00Z",
  "repo": "owner/name",
  "branch": "main",
  "local_root": "/path/to/dir",
  "summary": {
    "identical": 120,
    "local_only_changed": 3,
    "remote_only_changed": 0,
    "drift": 1,
    "failed": 0
  },
  "files": [
    {
      "path": "notes/foo.md",
      "status": "drift",
      "local_sha": "abc...",
      "remote_sha": "def...",
      "local_mtime": "2026-04-26T18:00:00Z",
      "remote_last_commit_at": "2026-04-26T22:30:00Z",
      "is_binary": false
    }
  ]
}
```

스키마 안정성 보장:

- `schema_version`: 호환성 깨는 변경 시 major 증가. v0.1은 `"1.0"`.
- `status` enum 동결: `identical` / `local_only_changed` / `remote_only_changed` / `drift` / `failed`. 추가는 minor 버전, 제거·이름 변경은 major.
- 시간 필드: 모두 ISO-8601 UTC (`Z` suffix). 로컬 타임존 출력 금지.
- null 정책:
  - 원격 only 파일: `local_sha=null`, `local_mtime=null`.
  - 로컬 only 파일: `remote_sha=null`, `remote_last_commit_at=null`.
  - identical 파일: 정상 SHA + 시간.

`--summary-only` 출력은 위 JSON에서 `files` 배열 제거 (다른 필드는 유지).

## 품질 게이트

- **Unit test coverage ≥ 80%** (cargo-tarpaulin 라인 커버리지 기준).
- GitHub API는 `mockito`로 mock하여 unit test에 포함.
- CI에서 80% 미달 시 빌드 실패. 합의된 강제 조건.
- 통합 테스트(임시 디렉토리 + mock HTTP 서버)는 별도 카운트, 80% 게이트엔 미반영.
- **Windows 환경 메모**: tarpaulin은 Windows에서 LLVM 백엔드(`--engine llvm`)를 기본 사용. ptrace는 Linux x86_64 전용. LLVM 백엔드는 non-zero exit code 처리·thread safety에 알려진 함정 있음 → Windows CI 환경에서 false positive·negative 발생 시 `--engine` 옵션 또는 fallback 도입 검토.

## Pitfall 메모

- **본 도구의 SHA는 git 표준이 아님** (위 "해시 정의" 섹션 참조).
- **GitHub Trees API truncation**: 응답 7MB 또는 약 10만 entry 중 먼저 도달 시 truncate. v0.1은 빠른 실패. sub-tree 재귀 다운로드는 Phase 4 또는 Phase 5에서 검토.
- **Rate limit**: 인증 토큰 시간당 5,000 req. Commits API 호출은 차이 있는 파일에만 한정.
- **Windows 경로**: GitHub은 forward slash, 로컬은 OS 의존. 비교 키는 forward slash로 통일.
- **mtime 신뢰성**: iCloud·복사·touch로 갱신 가능. 시간 비교는 휴리스틱.
- **캐릭터 인코딩**: 텍스트 판정 후 UTF-8 가정. 비-UTF-8(예: EUC-KR)은 바이너리 취급 → CRLF 차이로 영구 drift 가능 (Phase 5에서 다룸).
- **Cargo.lock**: 본 프로젝트는 binary CLI이므로 commit 대상.

## 검증 시나리오 (수동 v0.1)

- 로컬·원격 동일 → 모두 `identical`.
- 로컬에서 한 파일 수정 → `local_only_changed` 1건.
- 원격에서 한 파일 수정 → `remote_only_changed` 1건.
- 양쪽이 같은 파일을 다르게 수정 → `drift` 1건.
- CRLF로 저장된 로컬 파일이 LF normalize 후 원격과 동일하면 `identical`.
- BOM 추가된 로컬 파일이 BOM 제거 후 원격과 동일하면 `identical` (`--keep-bom` 미지정 시).
- `--keep-bom` 켰을 때 BOM 차이 → `local_only_changed` 또는 `drift`.
- 바이너리(이미지) 파일이 동일 SHA면 `identical`.
- `.gitignore`에 패턴 + `--ignore` 인자 합집합 동작 확인.
- 토큰 미설정 → exit code 2, stderr 에러 JSON.
- Rate limit 초과 시뮬레이션 → exit code 3.
- Trees truncated 시뮬레이션 → exit code 5.
- `--summary-only` → `files` 배열 부재.
- `--status drift` → 해당 파일만 `files[]`에.
- 부분 해시 실패 → exit code 4, `summary.failed > 0`.

## Phase 로드맵

세션이 휘발해도 컨텍스트가 유지되도록 향후 단계를 명시한다.

### Phase 1 (v0.1) — 본 PRD 범위
- 명령어: `scan`, `diff`
- read-only
- 캐시 없음 (매번 fresh)
- 4분류 JSON 출력
- 운영 contract 6개 박힘 (custom error / exit code / stderr / stdout 분리 / partial failure / 인증·rate limit)
- 컨텍스트 폭발 방어: `--summary-only`, `--status` 필터
- JSON 스키마 v1.0 안정성 보장

### Phase 2 — 편의 명령어
- `gitless-sync init` — `gitless-sync.toml` 설정 파일 생성 도우미. 인터랙티브 또는 인자 기반.
  - 입력: `--repo`, `--branch` 등 인자 또는 prompt
  - 출력: 현재 디렉토리에 `gitless-sync.toml` 작성. 기존 파일 있으면 `--force` 없이 실패.
  - 실패 모드: 파일 권한, 기존 파일 충돌.
- (`status` 명령어는 `scan --summary-only`로 대체. 별도 명령어 만들지 않음.)

### Phase 3 — Write 도구 분리
- 별도 바이너리 `gitless-push`. scan 결과(JSON)를 stdin 또는 파일로 받아 GitHub API로 실제 push 수행.
- gitless-sync는 read-only 불변 유지.
- AI가 scan → 사용자 승인 → push로 명시적 단계 분리.
- workspace 안에서 `shared/`를 같이 사용.

### Phase 4 — 성능 최적화
- 로컬 SHA mtime 기반 캐시. 큰 vault에서 매번 전체 해시 계산 비용이 문제일 때만 도입.
- v0.1 성능 측정 결과를 보고 도입 여부 결정.
- Trees API sub-tree 재귀 fallback (truncated repo 지원).

### Phase 5 — 도메인 함정 정리 (명시적 단계)

> "언젠가는 터질 폭탄"이므로 비목표가 아닌 명시적 후속 단계로 박는다.

- macOS HFS+/APFS의 NFD 정규화 vs GitHub의 NFC 보존 (한글·악센트 파일명 깨짐)
- 대소문자 충돌 (Windows에서 `README.md` vs `Readme.md`가 동일 path key)
- 비-UTF-8 텍스트 인코딩 (EUC-KR 등) — 현재 바이너리 취급으로 영구 drift 발생
- submodule (Trees mode `160000`) entry 처리
- 심볼릭 링크 (Trees mode `120000`)
- 빈 파일 (`SHA-1("blob 0\0") = e69de29...`) 처리 검증
- 실행 권한 (Trees mode `100755` vs `100644`)
- `.gitattributes` 파싱 → git 표준 blob SHA 정확 재현 (선택적, 큰 변경)

## 미결 (Open Questions, v0.2.1 시점)

- 큰 파일(예: 10MB 이상) 임계치. 해시 메모리 사용량 + Phase 4 캐시와 연결.
- CI 플랫폼: GitHub Actions 가정. Windows 러너에서 tarpaulin LLVM 백엔드 안정성 1차 검증 필요.
